# Progress

## 2026-10-20 — Etap 1 (core + hub + CLI) — done

Built (TypeScript strict, ESM, zero runtime dependencies):

- `packages/core`: envelope crypto (AES-256-GCM via `node:crypto`, AAD =
  vault + object id, 512-byte padding, plaintext envelopes refused in
  encrypted vaults), keyring + recovery key (`RK-…`, checksum), account key
  (`rmb1_…`, hub URL + optional SPKI pin, checksum) and device tokens, entry
  model (markdown + JSON-valued frontmatter), L0/L1 views, secret guard,
  in-memory search (Polish diacritics folded), project identity from git
  remote, atomic writes + mkdir lock, local vault + outbox, hub client
  (`node:https`, SPKI pinning with first-contact probe), `RemboClient`
  (setup, remember, forget, sync, search, devices, hub set-url).
- `packages/server` (`rembo-server`): `node:sqlite` append-only log
  (idempotent puts, tombstones erase ciphertext), HTTP API v1 with protocol
  headers, bearer device tokens (hashes only), per-IP lockout, per-device
  token bucket, size limits, account scoping on every query; self-signed
  P-256 certificate generator (pure DER + OpenSSL signing); admin CLI
  (`serve`, `tls create`, `key create|list|revoke`, `account`, `device`,
  `status`, `backup`).
- `packages/rembo` (`rembo`): CLI `setup`, `remember`, `search`, `read`,
  `list`, `forget`, `sync`, `status`, `doctor`, `device list|revoke`,
  `hub set-url`, `--json` everywhere.
- Build: `npm run build` (esbuild single-file bundles: client 22.12+, hub
  24.16+). Tests: `npm test` (vitest), `npm run typecheck`.

DoD evidence (`npm test`, 47 tests, ~21 s):
- 3 clients, 1000 parallel operations (≈800 writes, ≈200 forgets) with
  interleaved syncs → identical entry sets and INDEX.md on all clients, every
  expected entry present, every forgotten one absent, empty outboxes.
- Hub database files (incl. WAL) contain none of the marker phrases; a
  positive control (device name, stored in clear) proves the scan reads them.
- Account isolation: another account's vault, keyring, objects and devices
  answer 404; listings show only own resources.
- Also: success criterion 2 (fact from A found on C with source), offline
  queue, secret refusal, device revocation, auth lockout, TLS pin match /
  mismatch, 10k-entry search < 200 ms, real CLI end to end; manual smoke test
  of the bundled CLIs on Windows.

## 2026-10-21 — Etap 1 audit and fixes

Security hardening after the automated review (commit "Harden client against
a malicious hub"): encryption flag sealed in the keyring, hub-supplied ids
validated before any file access, authenticated tombstones, right-most
`X-Forwarded-For`, limiter eviction instead of a global clear.

Audit fixes (`test/robustness.test.ts`, 59 tests + 1 environment skip):
- Forward compatibility: authentic records this version cannot read (newer
  entry format, unknown record kind, unknown key id after a future rotation)
  go to `vaults/<id>/deferred/` and are retried on every sync instead of
  being skipped for good; unknown frontmatter fields are kept (`extra`).
- A change the hub refuses as invalid (400/413) moves to `failed/` instead of
  blocking the queue; other push errors (403/404/409/429/5xx) no longer stop
  the pull (`status: partial`). `rembo sync --retry-failed`, counts in
  `status` and `doctor`.
- Uploads are batched by size (12 MiB of base64 per request; 200 items) —
  previously 200 large objects exceeded the hub's 16 MiB body limit and
  wedged the queue. The hub caps a changes page at ~8 MiB (streamed with
  `iterate()`), `more = last < head`; the client caps responses at 64 MiB.
- Pull loop stops when a page makes no progress and ignores records that
  would move the cursor backwards.
- Sync lock: heartbeat (`refresh()` per page/batch) and owner-checked
  release, so a long first sync is not taken over and an old holder cannot
  remove a newer lock.
- Setup is local-first: key and config are written before the vault is
  created on the hub; a dropped creation is finished by the next sync
  (`vault.pendingKeyring`); any other failure removes local files and
  revokes the just-registered device. The CLI prints the recovery key before
  the first sync, so no later error can swallow it.
- `forget` also forgets the versions an entry supersedes (`--only` for just
  one), so an older version cannot resurface; views are regenerated by the
  next lock holder even offline (`views.dirty`), so a forgotten entry leaves
  INDEX.md at once.
- Hub: malformed percent-encoding → 400 (was 500 + stack in the log).
- Hub-supplied text (error messages, device names) is stripped of control
  and bidi characters before printing (`untrusted()`); it will also reach
  models in Etap 2.
- TLS: a pin mismatch caused by a re-signed certificate is reported as
  interception, naming the issuer (`tls_intercepted`); untrusted
  certificates in domain mode give `tls_untrusted` instead of a stack trace.
  Found because Avast Web Shield on the dev machine intercepts TLS even to
  127.0.0.1 — pinning refused it, as designed. The TLS test detects such
  interception and checks the error instead of a direct connection.
- Packages ship `LICENSE` (copied at build).

`rembo update` is referenced by hints (426, deferred entries) and must exist
in Etap 2.

## 2026-10-21 — Etap 2 (Claude Code plugin + one-command install) — done

Built (`packages/rembo`):
- `src/snapshot.ts`: the session snapshot from the local views (project
  page, this machine's page, preferences, index) in a `<rembo-memory>`
  wrapper marked as data, hard cap 8000 characters, entry text fenced so it
  cannot close the wrapper.
- `src/hook.ts` + `rembo hook session-start|session-end`: exec-form hooks;
  SessionStart prints the snapshot as `additionalContext` and starts a
  detached `rembo sync`; SessionEnd starts a sync; silent when off or not
  set up; errors go to `~/.rembo/logs/rembo.log`, exit code always 0.
- `src/mcp.ts` + `rembo mcp`: dependency-free MCP stdio server (JSON-RPC,
  protocol 2024-11-05 … 2025-11-25) with `search`, `read`, `list`,
  `remember`, `forget`; instructions with the usage rules (other clients
  also get the index); in-memory index reloaded when `views.stamp` changes;
  quick pull (≤ 1.5 s) before reads when the last one is older than 30 s,
  pull every 60 s, push after writes; never crashes at start.
- `plugin/`: manifest, README, `hooks/mod.ts` (`/rembo on|off|status|sync|
  search|forget` without a model turn, "Rembo Mode On · ✓/↑n/offline" status
  line, toast after remember, per-session off by denying rembo tool calls,
  version guard) and `hooks/mod.test.ts` (5 tests, `claude plugin test`).
- `src/install.ts` + `rembo install|update|uninstall [--purge --yes]`,
  `rembo on|off`, `rembo snapshot`, `--claude-config`, `--no-plugin`;
  `rembo setup` installs the plugin after the first sync; `rembo doctor`
  checks the plugin. Settings are changed only through `claude plugin …`,
  with a backup of `settings.json` in `~/.rembo/backup/` first.

DoD evidence (`npm test`: 68 tests + 1 environment skip; `claude plugin
test packages/rembo/plugin`: 5 tests):
- `test/claude-e2e.test.ts` with an isolated `CLAUDE_CONFIG_DIR` and user
  profile: `rembo setup` installs the plugin (listed, enabled, validates),
  a real `claude -p` session gets the snapshot with an entry written before,
  loads the module ("Rembo Mode On") and starts the rembo MCP server;
  `rembo doctor` passes; `rembo uninstall` removes plugin and marketplace
  and leaves no "rembo" in settings.json; hashes prove the real
  `~/.claude` files were not touched. No model call (no credentials).
- `test/plugin.test.ts`: snapshot limits and fencing, hooks as real
  processes (answer, background sync, silence when off / not set up), MCP
  protocol and all tools over stdio, cross-process freshness, no crash.
- SessionStart hook: 136 ms median at 1000 entries (budget 300 ms).

Found and fixed on the way: a 2 s unref-less timer kept every hook process
alive; the background sync inherited the project folder as its working
directory (Windows cannot delete or rename it while the sync runs).
