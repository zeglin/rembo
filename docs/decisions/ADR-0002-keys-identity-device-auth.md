# ADR-0002: Keys, identity and device authentication

- Status: proposed (revised 2026-10-20: bearer tokens instead of signatures)
- Date: 2026-10-20
- Research: docs/research/platform.md §m

## Decision

Three secrets, each with one job:

| secret | generated by | hub stores | purpose |
| --- | --- | --- | --- |
| **account key** `rmb1_...` | `rembo-server key create` (cloud: provisioning) | SHA-256 of its secret | registers devices; revocable; device limit per plan |
| **device token** `rmbd_...` | hub, at registration | SHA-256 | authenticates every API request; revocable per device |
| **recovery key** `RK-...` | first device | nothing (only a keyring encrypted with it) | unlocks the vault on new devices (ADR-0005) |

### Account key format

`rmb1_` + base64url(version | flags | key_id[8] | secret[32] |
[cert_sha256[32]] | [hub host:port]) + 4-byte checksum.

- `hub` absent = default cloud hub. `cert_sha256` present = IP-mode hub with a
  pinned certificate key (ADR-0003).
- The checksum catches paste errors with a clear message.
- `rembo hub set-url <url>` changes the stored address without re-joining.

### Registration and requests

- `POST /v1/devices` with `Authorization: Bearer <account key secret>` and
  `{name, platform}` -> `{device_id, token, account_id, vaults}`. The account
  key secret crosses the network once per device, inside (pinned) TLS.
- Every other request: `Authorization: Bearer rmbd_<device_id>.<secret>`.
  Lookup by id, constant-time compare of SHA-256, uniform `401` (no
  enumeration), lockout after repeated failures per IP.

### Why bearer tokens, not per-request signatures

Signatures would keep the secret off the wire, but cost a canonical string,
a nonce cache, clock-skew handling and reverse-proxy path pitfalls. With E2E
encryption the stakes are low: a stolen device token can download ciphertext
and delete records, but cannot read or forge memory (AEAD). A leaked hub
database gives only hashes of high-entropy secrets: no working credentials.
mTLS was rejected as well (breaks behind TLS-terminating proxies).

### Devices

- Roles `full` (default) and `read-only` (less trusted machines; enforced on
  writes).
- A device may list and revoke devices of its own account
  (`rembo device list|revoke`): account self-service, needed in cloud.
  Hub administration (keys, accounts, backups) stays CLI-only on the server.
- After revoking a device, `rembo vault rotate` is offered (ADR-0005).
- `rembo device link` (join without typing the recovery key: the new device
  shows a code, an existing device approves and sends the keyring) is
  designed for later.

## Consequences

- Standard, easy-to-debug auth; works behind any reverse proxy.
- Token theft (e.g. from a proxy that logs `Authorization`) allows deletion,
  mitigated by revocation, daily hub backups, and local copies on every
  device.
